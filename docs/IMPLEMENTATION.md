# 实施路线图

按阶段推进，每个阶段产出可验收的成果，避免一次性铺太大。

---

## 阶段 0：本地验证（今天就能做完，0 成本）

**目标**：用你现有的 Docker 把服务端跑起来，确认链路通。

```bash
cd server && cp .env.example .env
python rdctl.py start
python rdctl.py key        # 拿到公钥
```

用官方 RustDesk 客户端（[下载](https://github.com/rustdesk/rustdesk/releases)）验证：
设置 → 网络 → 解锁网络设置 → ID 服务器填 `<你的IP>`、Key 填上面拿到的公钥。
两台机器互连成功即通过。

> **测试环境限制**：当前测试机没有公网 IP，跨 NAT 场景（员工在家连公司电脑）
> 无法在这个阶段验证。只有同网段的机器之间能直连。

**验收**：两台机器可控。

## 阶段 1：定制客户端

按 `../README.md` 的「快速开始」走 GitHub Actions 路线。

先把 `.github/workflows/flutter-build.yml` 里不需要的平台注释掉——
默认会构建 Linux/macOS/Android/iOS，**全跑一遍要几小时**。只留 Windows x64 能省下大量时间。

**验收**：拿到 exe，装到同事机器上，不填任何配置就能连。

## 阶段 2：上公网服务器

### 配置建议

建议用轻量应用服务器即可。

| 项 | 推荐 | 说明 |
|---|---|---|
| CPU / 内存 | 1 核 2G 起 | hbbs/hbbr 极轻量，CPU 主要做 ID 注册查询；但云厂商最低配常是 2核2G，直接选最便宜的即可 |
| 操作系统 | Ubuntu 22.04 / 24.04 LTS | Docker 生态最好 |
| 带宽 | **3–5 Mbps 起步** | 关键指标，见下方说明 |
| 地域 | 离团队成员最近 | 中继流量都走这里，延迟影响操作手感 |

> **带宽怎么估**：hbbs/hbbr 本身几乎不占带宽，占的是**中继流量**。
> 走 P2P 时只消耗几 KB/s；打洞失败转中继时：
> - 纯办公操作（文档、表格）：约 100 KB/s
> - 1080p 动态画面：300 KB/s ~ 3 MB/s
> **同一时期有 3 个人连**、且都走中继，建议按 5 Mbps 规划。

### 部署要点

1. 云服务器上装 Docker，把 `server/` 目录传上去
2. 改 `.env`：`RELAY_HOST` 换成公网 IP 或域名
3. 上 Linux 后建议把 compose 里的 `ports:` 换成 `network_mode: "host"`，
   好处是服务端能拿到真实客户端 IP（便于审计），且少一层 NAT 转发
4. 安全组放行 **TCP 21115 / 21116 / 21117 + UDP 21116**
   （21118/21119 是 Web 客户端用的，不要开，原因见 docker-compose.yml 内注释）

### 稳定性建议

```bash
# 放进 crontab，每天备份密钥与连接记录
0 3 * * * cd /opt/rd/server && python rdctl.py backup

# 密钥一旦丢失，所有已分发客户端都要重换，务必异地留一份
# 定期清理旧备份，避免磁盘占满
```

**验收**：跨 NAT 的两台机器（例如一台在公司、一台在家）能互連。

## 阶段 3：团队运营（可选）

把运维动作固化下来：

- **设备台账**：定期从服务端的 SQLite 导出设备清单，标注 ID 对应的责任人
- **分发方式**：内网文件服务器或企业微信/钉钉内部分发，exe 建议用内部签名避免 SmartScreen 拦截
- **版本升级**：上游 RustDesk 发新版时，同步 fork → 重跑 `patch-ci.py` → 重新触发 CI
- **应急通道**：保留一份官方客户端备用——万一自建服务器挂了，至少还有官方公共服务器可用

---

## 成本提示

自建方案的成本主要在云服务器+带宽；相比 ToDesk/TeamViewer 商业授权，团队规模越大越划算。

另外，如果将来需要做**账号体系、设备分组、连接审计**，
RustDesk Server Pro 是官方付费版（自带 Web 控制台）。
但对于小团队，自建 + SQLite 审计通常够用。
