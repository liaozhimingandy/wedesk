# 08 · 性能调优

> 目标：让画面最流畅、CPU 最省、服务端和客户端长期运行占地最小。
>
> **一句话结论**：性能的大头在**编解码**，而编解码的胜负手是**开没开硬件编解码**。
> 其余参数（画质、帧率、编解码器）都是数量级更小的微调。
> 调参之前先确认 `--hwcodec` 真的编进去了，否则后面全是在小数上较劲。

**前一篇**：[05 · 定制指南](./05-customize.md)　|　**相关**：[03b · 云构建](./03b-ci.md)、[04 · 部署指南](./04-deploy.md)

## 一、性能由什么决定

一次远程桌面的数据链路，耗时与 CPU 开销集中在中段：

```mermaid
flowchart LR
    A["抓屏<br/>DXGI / GDI"] --> B["转换<br/>libyuv"]
    B --> C["编码<br/>★ 最大开销"]
    C --> D["网络<br/>P2P 或中继"]
    D --> E["解码<br/>客户端"]
    E --> F["渲染<br/>Flutter"]

    style C fill:#ffe0e0,stroke:#c00,stroke-width:2px
    style A fill:#e8f0ff,stroke:#36c
```

| 环节 | 软件编码时的大致开销 | 说明 |
|---|---|---|
| 抓屏 | 低 | Windows 默认走 **DXGI**（GPU 路径）。退回 GDI 会明显变重 |
| 颜色转换 | 低 | libyuv，SIMD 优化过 |
| **编码** | **高，占绝大部分** | 软件 VP9/AV1 单路 1080p30 可吃掉一个核心的 30–60% |
| 网络 | 取决于链路 | P2P 直连几乎零成本；中继要占服务器带宽 |
| 解码 / 渲染 | 低 | 客户端侧，硬件解码普遍可用 |

所以三个开关的收益排序是：

1. **硬件编解码**（量级差距，CPU 从数十个百分点降到个位数）
2. 编解码器选择（相同硬件条件下差 20–40%）
3. 画质与帧率（线性，且牺牲的是观感）

## 二、开关一：硬件编解码（最重要）

### 它做了什么

开启后，被控端用显卡上的专用编码单元（NVIDIA **NVENC** / Intel **QSV** / AMD **AMF**）代替 CPU 软件编码。
专用单元是独立于 CPU 的硬件模块，编码几乎不占 CPU，延迟也更低。

`--vram` 进一步让编码直接在显存中进行，省去一次内存往返。

### 怎么开

| 场景 | 做法 |
|---|---|
| GitHub Actions | `hwcodec` 输入**默认为 true**，直接跑即可 |
| 本地构建 | `build-local.bat`（默认带 `--hwcodec --vram`） |
| 本地想跳过 | `set NO_HWCODEC=1` 后再跑，省下 60–150 分钟的 FFmpeg 编译 |

### 代价

FFmpeg 需要从源码编译，是整条流水线最慢的一环：

| | hwcodec 开 | hwcodec 关 |
|---|---|---|
| 首次构建 | **+40–90 分钟**（CI）/ 60–150 分钟（本地） | 基线 |
| 后续构建 | 命中二进制缓存后大幅缩短 | 基线 |
| 运行 CPU | 个位数百分比 | 数十个百分点 |
| 编解码 | 硬编 + 软编兜底 | 仅软件 VP9/AV1 |

**建议**：保持开启。构建慢是一次性的，运行省 CPU 是永久的。
CI 用了 vcpkg 的 `x-gha` 二进制缓存、本地用了 `files` 缓存，第二次起会快很多。

### 怎么确认真的编进去了

构建时看日志里有 `hwcodec` feature 生效；运行时在被控端机器上开任务管理器远程一路，
CPU 明显低于软件编码。也可以在客户端会话里看画面信息显示的编码器名称。

## 三、开关二：编解码器

`设置 → 画面 → 编解码器`，对应配置项 `codec-preference`，默认值 **auto**。

| 编解码器 | CPU 开销 | 带宽 | 适用 |
|---|---|---|---|
| **auto** | 取决于可用硬件 | — | **推荐**。开启 hwcodec 后会自动挑硬件编码器 |
| h264 / h265 | 最低（硬件） | 中 | 有硬编时的实际选择 |
| vp9 | 中（软件） | 中 | 无硬件编码时的稳妥选择 |
| av1 | **最高**（软件） | 最低 | 只在带宽极其紧张时考虑 |
| vp8 | 低 | 高 | 兼容性兜底 |

**取舍逻辑**：

- 内网 / 团队同网 → 带宽不是瓶颈，**优先省 CPU**：auto（走硬件）或 vp9
- 跨公网、带宽紧张 → av1 省带宽，但要接受被控端 CPU 升高
- 开启 hwcodec 后保持 **auto** 即可，让程序挑硬件编码器

## 四、开关三：画质与帧率

默认值已经是比较均衡的位置，只在明确需要时再动。

| 配置项 | 默认 | 调低的收益 | 代价 |
|---|---|---|---|
| `image-quality` | `balanced` | CPU 与带宽下降 | 画面糊，文字边缘明显 |
| `custom-image-quality` | 50 | 同上（自定义档位） | 同上 |
| `custom-fps` | 30 | 线性省 CPU 与带宽 | 鼠标拖动、滚动的跟手感变差 |

**建议**：办公场景（文档、表格、远程协助）保持默认。
只有在被控端是老机器、或同时被多路连接时，才把帧率降到 15–20。

## 五、网络路径：P2P 还是中继

这是**延迟**与**服务器带宽**的取舍，比画质参数影响更大。

| | P2P 直连 | 中继（hbbr） |
|---|---|---|
| 延迟 | 最低，走内网直连 | 多一跳 |
| 服务器带宽 | **不占** | 全部画面流量经过服务器 |
| 连通率 | 依赖 NAT 类型，复杂网络可能打洞失败 | 几乎 100% |

- 内网 / 同网团队：`ALWAYS_USE_RELAY=N`（默认），走 P2P，服务器几乎零带宽压力
- 成员分散在不同网络：可设 `ALWAYS_USE_RELAY=Y` 提高连通率，但**先确认服务器出网带宽够**
  —— 一路 1080p 画面大约 2–5 Mbps，十路并发就是 20–50 Mbps

## 六、服务端资源占用

`server/deploy/docker-compose.yml` 已内置上限，默认值按 50 人以内团队给出。

| 服务 | 常驻内存（量级） | 默认上限 | 瓶颈 |
|---|---|---|---|
| hbbs | 10–40 MB | 256 MB | 不是瓶颈，只在注册/心跳时忙 |
| hbbr | 随并发路数增长，每路几 MB 缓冲 | 512 MB | **出网带宽**，不是内存 |

已经做的三件事：

1. **内存与 CPU 上限** —— 异常时快速重启，而不是拖垮宿主机
2. **日志轮转** —— 单文件 10 MB、保留 3 份，防止长期运行写满磁盘
3. **`RUST_LOG` 默认 `warn`** —— info 级别下每次注册/心跳都落一行，长期运行的磁盘写入可观；排障时临时调高即可

> 内存数字是量级参考，不是实测承诺。真实占用请用 `docker stats` 观察自己的负载。

## 七、客户端（被控端）资源占用

被控端是常驻进程，空闲时应当接近零占用。

| 状态 | 预期占用 |
|---|---|
| 空闲（无人连接） | CPU 接近 0，内存几十 MB |
| 单路 1080p 会话（硬编） | CPU 个位数百分比 |
| 单路 1080p 会话（软编） | CPU 数十个百分点，随画质帧率变化 |

**空闲时 CPU 偏高**的排查顺序：

1. 抓屏是否退回 GDI —— DXGI 是 GPU 路径，GDI 会明显变重
2. 是否开着**自动录制**（`allow-auto-record-incoming`）—— 会持续编码写盘
3. 日志级别是否被改成 debug/trace
4. 是否有多路会话残留

## 八、验收方法

改完之后别凭感觉，用这两个办法量：

```bash
# 服务端：看真实占用，确认上限设置合理
docker stats rd-hbbs rd-hbbr
```

被控端：连一路会话，在任务管理器里看进程 CPU。
对比 hwcodec 开/关两次构建，差距应当是**量级级别**的——如果只是差了几个百分点，
说明硬件编码没真正生效，回头检查 FFmpeg 头文件是否编进去了。

## 九、常见误解

| 说法 | 实际情况 |
|---|---|
| "画质调低就能省 CPU" | 有帮助，但远不如开硬件编解码，后者差一个量级 |
| "服务端要很大内存" | hbbs 只要几十 MB；hbbr 的瓶颈是带宽不是内存 |
| "AV1 一定最好" | AV1 省带宽但软件编码最费 CPU，内网场景反而更差 |
| "hwcodec 编不过就关掉" | 关掉能编过，但每次运行都在付 CPU 的代价。先查 `VCPKG_DEFAULT_HOST_TRIPLET` |

> hwcodec 编译失败时，报错是 `mfx_encode.cpp(3): fatal error C1083: 'libavcodec/avcodec.h'`。
> 根因与解法见 [07 · 故障排查](./07-faq.md)。
